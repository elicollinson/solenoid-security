## Concurrency and likely duration

The harness now defaults to **48** concurrent pinned chunk workers and accepts `--concurrency=1` through `--concurrency=64`. Each worker processes one case/backend task sequentially, so the requested limit bounds simultaneous OpenRouter calls while many other case tasks can make progress. The 400 Model Armor full-text calls remain sequential and separate from this pool. The completed 339-case NotInject run at eight workers dispatched 2,630 chunk calls in 7.20 minutes, about **6.1 calls/second**. A purely linear extrapolation would make 46,010 chunk calls take approximately **21 minutes at 48 workers** or **16 minutes at 64**, plus roughly one minute for Model Armor. These are optimistic estimates: longer task tails, provider capacity, 429s, and retry cooldown can make the actual duration substantially longer. No LLMail calls were made to benchmark the higher setting.

[OpenRouter's current pricing page](https://openrouter.ai/pricing/) describes paid-plan rate limits as passthrough from the provider(s); it does not publish a numeric limit for this exact TypeSafe/DeepInfra pair. [Google's Model Armor quota page](https://docs.cloud.google.com/model-armor/quotas) lists 1,200 API queries per minute per project, shared with other applications. The sequential 400-call Armor phase stays below that published per-minute default in the earlier 359-call local timing, though other project traffic can use quota.

For OpenRouter, a shared adaptive gate starts at the selected concurrency. On an explicit HTTP 429, it honors `Retry-After` when present (bounded to 30 seconds), otherwise uses bounded exponential backoff, halves new-send capacity at most once per second, and gradually restores one slot per 100 successful responses. It retries **only** explicit 429 responses, up to six attempts total per chunk; model/provider pins and response checks remain unchanged. Every HTTP attempt is a `dispatch` event in the ignored checkpoint and counts toward the 50,000-call cap; 429 responses have separate `rateLimit` events. Successful Gemma response bodies and generation IDs are checkpointed before returning to the production Agent, which may need another structured-output turn for the same chunk. Network failures, timeouts, 5xx responses, and provenance failures do not trigger another network request. A checkpoint with an uncertain error or a dispatched request lacking a recorded outcome requires inspection and an explicit `--retry-uncertain` resume choice; provenance failures always stop. This avoids automatic duplication of a possibly charged success after a crash.
